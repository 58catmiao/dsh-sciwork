# 决策：科研模式重构为「一条能力清单 + 两块屏幕」

- 日期：2026-10-21
- 状态：**已选定方案 A**，待实施
- 详细方案：[PLAN-0.3.md](./PLAN-0.3.md)

## 背景

`dsh-sciwork` 已经是可用的科研插件：一个面板、24 个宿主动作、Python 引擎、Origin MCP、5 个技能、14 天周期门禁。
但随着功能变多，出现三个结构性问题：

1. **两个入口各说各话**：面板点按钮是一套路径，聊天里让智能体干活是另一套，用户得在中间搬信息。
2. **「当前在做什么」没有唯一事实**：面板看到的库和智能体理解的上下文对不上。
3. **公开给别人的成本高**：动作、UI、安装各自演进，新增功能要改好几处。

## 约束（用户确认）

| 编号 | 约束 |
|---|---|
| R1 | 面板点按钮与聊天直接办事，两条入口都要（不能二选一） |
| R2 | 以后公开给别人用，本次是既有开源项目的更新 |
| R3 | Python 引擎与 Origin 必须保留，整体必须待在 DSH 里 |
| R4 | 确定的活交给脚本，判断与创作交给预设 agent |
| R5 | 覆盖「选题 → 实验设计 → 数据分析绘图 → 论文撰写 → 投稿」全流程 |
| R6 | UI 现代、简洁、表意清楚 |

## 考虑过的方案

- **A（选定）一条能力清单 + 两块屏幕**：所有操作登记进唯一动作表，面板 / agent / CLI 共用；课题作为一等公民，面板与 agent 读同一份状态。
- **B 对话主驾**：聊天为主入口，面板退化为仪表盘。与 R1 的「按钮入口」冲突，排除。
- **C 最小改造**：给现有面板加一条对话通道。只解一半 R1，公开化仍要重做，半年后仍会走到 A，排除。

## 决定

采用 **方案 A**。决定性理由：R1 的两个入口本身互相拉扯，只有「一套状态、两个入口」能让它们同时成立；
B 丢按钮，C 补一半，且 C 之后必然重写成 A。

## 已确认的子问题

| 问题 | 决定 |
|---|---|
| 旧库怎么办 | 先完整备份；双读兼容；迁移在副本上验证通过后再切换（详见 PLAN-0.3 §11） |
| 公开版数据边界 | 只承诺「库在本机文件夹」；放同步盘属于「可用但不背锅」的兼容项，加锁与冲突检测 |
| 公开程度 | 仓库已开源，本次作为 **0.3.0** 更新发布，不新开项目 |
| 重构期旧面板 | 旧标签页保留到新工作台可用；新 UI 以特性开关灰度启用 |

## 后果

- 动作表成为唯一事实源：新增功能先登记动作，再谈 UI 与 agent。
- 旧的 24 个动作名保留为别名，端点和信封不变，旧面板在迁移期继续可用。
- Python 引擎保持原样，只加稳定契约与适配层；Origin 仍经 MCP。
- 0.3.0 需要一次数据模型迁移（每课题一份 `project.json`），迁移必须可回滚。
- 前端沿用**零构建、零第三方依赖**（现有约束），靠设计令牌与组件化把界面做现代，而不是引入框架。
